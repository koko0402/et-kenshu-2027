第19回 本物のプログラムを仮想コースで走らせる

第11回・第12回のシミュレータは、練習用に自分で書いたプログラムを走らせるものでした。この回は、2026年の本物の走行体のプログラムを、PCの上で動かします。ハブとカメラだけを偽物に差し替えて、判断はすべて実機と同じプログラムでします。実機が無くても、走りの組み立てが崩れていないかを何百回でも確かめられます。

用意するもの：第18回で Python を入れたPC

説明

単体テスト

走行体のプログラムのうち、機械にさわらない部分（PID の計算、起動オプションの読み取り、ETラリーの道順の計画など）は、PCだけで確かめられます。test/test_*.c に、「この値を入れたらこうなるはず」という確認を書いてあります。これを単体テストといいます。

assert(delivery_math_color_from_hsv(5, 80, 55) == DELIVERY_BOTTLE_RED);

assert(式) は「この式が正しいはず」という確認で、正しくなければ、その行で止まって式とファイル名と行番号を出します。テストが落ちたら、テストが間違っているのか、プログラムが間違っているのかを考えて、正しいほうに合わせます。テストを消して OK にするのは、直したことになりません。

ドリルの check.sh も、同じしくみで作ってあります。

シミュレータ

test/simulator/ に、ハブとカメラの偽物があります。モータへの指示を受けて仮想の走行体を動かし、センサの値を返します。走行体のプログラム（src/app.c など）はそのまま使うので、実機と同じ判断をします。時間は待たないので、120秒の走りが1秒もかからずに終わります。

seed（種）を変えると、滑り、左右の差、回る量、ジャイロの遅れ、QRの読みにくさがばらつきます。同じ seed なら毎回同じ走りになるので、失敗した seed を何度でも再現できます。

シミュレータは実機の代わりにはなりません。道順と、失敗したときの立て直しが崩れていないかを確かめる道具です。実機で起きたことはシミュレータにも入れておくと、次から自動で確かめられます。

手順

  1. ETrobo のフォルダで、単体テストを走らせる

    $ cd ~/Desktop/ETrobo
$ sh scripts/local_test.sh

    最後まで OK test_… が並べば、全部通っています

  2. シミュレータをビルドする

    $ mingw32-make build/rally_sim

  3. 1回走らせて、ブラウザで再生する

    $ python scripts/sim_view.py --bottles --seed 3

    logs/sim_view_bottles.html をダブルクリックして、▶ で再生します。右のメッセージは、実機のログと同じものです

演習

演習19-1　テストを落としてみる

test/test_delivery_math.c の確認を1つ、わざと違う色に書き換えて、sh scripts/local_test.sh を走らせてください。何と出ましたか。読んで、どの行の何がおかしいと言っているか説明してください。終わったら git restore test/test_delivery_math.c で戻します。

演習19-2　走りを見る

演習の手順3で再生した走りについて答えてください。

  1. ボトルの色は何色でしたか。何で判定しましたか
  2. 南東の角で何をしていますか
  3. 力士ボトルはどうやって見つけましたか
答え 1. メッセージの「ボトルの色は黄です」など。アームを上げて前を向けたカラーセンサと、近づく間のカメラの両方で数えている。 2. 線が直角に北へ折れていて、縁をたどるだけでは曲がり切れないので、線が切れた所で止まり、少し下がってジャイロで北を向いている。 3. 土俵の東で、左右に回りながら超音波センサの距離を見て、いちばん近い物の向きを探している。

演習19-3　seed を変える

--seed を1〜10で変えて走らせてください。全部同じ動きにならないのはなぜでしょう。

演習19-4　100回まとめて

$ sh scripts/rally_sim.sh ./build/rally_sim.exe 100 1 -- --from-main --bottles --no-calibration

成功率と、かかった時間が出ます。失敗した回があれば、logs/rally_sim/run_<seed>.txt を grep -v "^\[" で読んで原因を探してください。

回数を書き忘れると「試行 0 回」と出ます。成功率0％ではなく、走っていないだけなので慌てないでください。

演習19-5　速さを変えて比べる

config/parameters.h の DELIVERY_CARRY_SPEED（ボトルを抱えて線をたどる速さ、今は30）を25と35に変えて、それぞれ演習19-4を走らせてください（変えたらビルドし直す）。遅いほうが確実そうなのに、25で成功率が下がるのはなぜでしょう。

終わったら必ず30に戻してください（git diff config/parameters.h で確かめる）。

答え 2026年10月の結果では、25が100回中70回、30が300回中299回、35が75回だった。25だと左右の出力が、車輪が回り出すぎりぎり（静止摩擦）に近くなって、曲がる側の車輪が止まってしまう。遅いほど安全とは限らない。
