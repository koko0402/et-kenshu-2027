第9回 ファイルの分け方と make

ここまでは1つのファイルにプログラムを書いてきました。本物の走行体のプログラムは、100個近いファイルに分かれています。この回は、なぜどうやって分けるのかと、たくさんのファイルをまとめてコンパイルする make の使い方を覚えます。

用意するもの：これまでのドリル

説明

なぜファイルを分けるのか

走行体のプログラムを1つのファイルに全部書くと、何万行にもなって、どこに何があるか分からなくなります。だから「モータを動かす」「ライントレースする」「自分の位置を計算する」のように、役割ごとにファイルを分けます。

2026年のプログラムは、src/ の中を次のように分けていました。

フォルダ 役割
src/device/ モータ・センサ・ハブとのやり取り（機械に直接さわる所）
src/control/ ライントレース・まっすぐ進む・その場で回る
src/judge/ PID の計算、値をなめらかにする
src/localization/ 自分の位置を計算する
src/recognition/ カメラとのやり取り、QRコード
src/obstacle/ 難所（ETラリー・ET相撲・デリバリー）の攻め方
src/section/ 区間ごとに速さや PID の値を切り替える
src/competition/ スタート待ち、キャリブレーション、時間の管理

.c と .h

1つの部品は、.c と .h の2つのファイルで作ります。

motor.h（ヘッダ）には「こういう関数がある」という宣言と、構造体の形を書きます。motor.c（ソース）には関数の中身を書きます。ほかのファイルからモータを使いたいときは、#include "motor.h" と書いて宣言を読み込みます。

/* motor.h */
#ifndef ETROBO_MOTOR_H
#define ETROBO_MOTOR_H

void motor_set_power(Motor *self, int power);

#endif

最初と最後の #ifndef・#define・#endif は、同じヘッダが2回読み込まれても困らないようにするための決まった書き方です（インクルードガード）。関数の名前は「部品の名前_すること」（motor_set_power）にそろえています。

数字に名前を付けて1か所に集める

#define SPEED_LINE_TRACE_DEFAULT   70
#define LAP_GATE_DISTANCE_MM     5400

#define で名前を付けた数字は、コンパイルの前に本物の数字に置き換わります。2026年のチームは、速さや距離などの数字をプログラムの中に直接書かず、全部 config/parameters.h に名前を付けて集めていました。実機で調整するとき、直す場所が1か所で済むからです。

状態に名前を付ける enum

typedef enum {
    RACE_PHASE_BEFORE_START,   /* スタート合図待ち */
    RACE_PHASE_LINE_TRACE,     /* 前半走行 */
    RACE_PHASE_OBSTACLES,      /* 難所攻略中 */
    RACE_PHASE_RETURNING,      /* ガレージ帰還中 */
    RACE_PHASE_FINISHED        /* フィニッシュ */
} RacePhase;

これは本物の src/competition/race_scenario.h にあるものです。第8回でやった状態機械の「状態」に名前を付けています。

関数ポインタ（少し難しい）

ETラリー、ET相撲、デリバリーは、どれも「始める」「1回分進める」という同じ形の処理を持っています。C には「関数の場所」を入れておく変数（関数ポインタ）があるので、難所ごとに自分の関数を入れた表を作っておき、使う側は難所の種類を気にせず同じ呼び方で動かせるようにしています（src/obstacle/obstacle.h）。第13回で出てくるクラス図の「汎化」を、C で書いた形です。

make

ファイルが増えると、gcc のコマンドが長くなります。どのファイルをどの順でどうコンパイルするかを Makefile に書いておいて、make の一言で済ませるのが make です。変わったファイルだけ作り直してくれるので、時間もかかりません。Windows では make の代わりに mingw32-make と打ちます。

第11回で使うシミュレータの Makefile は短いので、読んでみるとしくみが分かります。

entry_sim: $(SIM_SRC) my_robot.c $(HEADERS)
	$(CC) $(CFLAGS) -o $@ $(SIM_SRC) my_robot.c $(LDLIBS)

1行目は「entry_sim を作るには、これらのファイルが要る」、2行目は「作り方」です。2行目の先頭は空白ではなくタブでないといけません。

よくあるエラー

undefined reference to 'xxx' は、関数の宣言はあるけれど中身が見つからない、という意味です。中身の書いてある .c をコンパイルに入れ忘れています（Makefile の一覧に足す）。

implicit declaration of function は、#include を忘れて、知らない関数を使っているという意味です。

Segmentation fault は、プログラムが動いている途中で落ちたという意味です。配列の範囲の外を使った、ポインタが何も指していないまま使った、が多いです。

手順

  1. docs/後輩育成/新人研修2027/シミュレータ/ を VS Code で開いて、robot_api.h、world.h、world.c を順に見る。.h に何が書いてあって、.c に何が書いてあるかを見比べる

  2. ターミナルでそのフォルダに入って、ビルドする

    $ cd ~/Desktop/ETrobo/docs/後輩育成/新人研修2027/シミュレータ
$ mingw32-make clean
$ mingw32-make

    最初に gcc の長いコマンドが1行出て、そのあとシミュレータが走ります。もう一度 mingw32-make を打つと、今度は gcc の行が出ません。何も変わっていないので、作り直さなかったからです

演習

演習9-1　何が起きるか試す

シミュレータの Makefile の SIM_SRC から judge.c を消して、mingw32-make clean してから mingw32-make してください。どんなエラーが出ますか。終わったら元に戻してください（git restore Makefile）。

答え `undefined reference to 'judge_init'` などが出る。judge.h で宣言はされているので main.c のコンパイルは通るが、最後につなげる（リンクする）ときに中身が見つからない。

演習9-2　関数ポインタ

docs/後輩育成/練習/02_C言語/04_関数ポインタ.c を開いて、ET相撲の表を書き、難所を順に動かす部分を完成させてください。完成すると、デリバリーと ET相撲のメッセージが順に出て、最後に「難所を全部終えました」と出ます。

ETラリーを足すとき、main のループや obstacle_execute() を書き換える必要はあるでしょうか。

答え 無い。ETラリー用の関数と表を作って、配列に足すだけで済む。これが関数ポインタの表で作る良さ。答えのコードは同じフォルダの `答え/` にある。

演習9-3　本物を探す

config/parameters.h を開いて、ライントレースの速さを決めている #define を探してください。その値を使っている所を、Ctrl + Shift + F で探してください。
