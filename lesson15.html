第15回 審査で見られるモデル

ここまでの図は、主に「どう作るか」の図でした。アプライドクラスの地区大会の審査で求められたのは、もっと手前の「何を作るか、なぜそれを作るか」の図です。2026年のチームはここを外してしまいました。この回は、その反省と、審査で求められる図の考え方をやります。

用意するもの：なし

説明

2026年の反省

2026年の東海地区大会では、アプライドクラスのモデル審査の対象は ETラリーだけで、提出する範囲はアブストラクト（概要）、要求モデル、システム分析モデルでした。

うちのチームは6ページのモデルを提出しましたが、そのうち半分は設計モデルと制御モデル（第13回で見たパッケージ図・クラス図・状態機械図など）で、審査の範囲の外でした。講評でも、力を入れた部分の多くが評価の対象にならなかったこと、システム分析が設計の細かさになってしまっていたことを指摘されました。

毎年、まず審査の規約を読んで、何が審査されるのかを確かめてから描き始めてください。規約は年ごとに変わります。

要求モデル

要求モデルでは、何を目標にするか、そのために何が必要かを決めます。

評価の高かったチームに共通していたのは、目標が数字になっていて、その数字に理由があることでした。「ETラリーをがんばる」ではなく「ETラリーで50秒以内に2周する」のように書いて、なぜ50秒なのか（120秒を各区間にどう配分したか）、なぜ2周なのか（1周に何秒かかるか）を説明します。

要求には番号を付けて、それぞれに「どう確かめるか」を数字で書きます。たとえば「ゲートの位置を正しく読む」という要求なら、「100回中99回以上正しく読める」のように書きます。

品質の観点（速さ、確実さ、直しやすさなど）で要求を出して、どれを優先するかを決めます。ISO/IEC 25010 という規格の、性能効率性、信頼性、保守性といった言葉を使うと、考えた範囲が伝わります。

リスクを出す（FMEA）

何が起きると困るかを、表にして考えます。これを FMEA（故障モード影響解析）といいます。

何が起きる 原因 どうなる 深刻さ 起きやすさ 対策
QRが読めない 走りながら撮って画像がぶれる ゲートの位置が分からない 5 3 止まってから撮る。読めなければもう一度撮る

深刻さと起きやすさを掛けて、大きいものから対策を考えます。対策は、要求として要求モデルに入れます。第13回のユースケース図のミスユースケース（困ること）と対策も、同じ考え方です。

システム分析モデル

システム分析モデルでは、作るものの中身ではなく、外との関係と、大きな役割分担を描きます。

まず、作るものの外にあるもの（コース、ヒントカード、審判、PCなど）と、それぞれとやり取りする情報を図にします。

次に、作るものを「何の責任を持つか」で、いくつかのサブシステムに分けます（情報を取る、計画する、走らせる、など）。機械の種類やプログラムのファイルで分けるのではありません。そこまで細かくすると設計になってしまいます。

最後に、それぞれのサブシステムをどの機械（ハブ、ラズパイ、PC）に置くかを決めます。案を2〜3個出して、優先する品質の観点ごとに点数を付けて比べ、なぜその案にしたかを書きます。

講評を読む

2026年の各チームの提出モデルと審査員の講評は、プロジェクトの docs/手がかり/モデルの参考/ に入っています（参加者に配られたものなので、外には出さないでください）。読む順番は、そのフォルダの README に書いてあります。いちばん評価の高かったチームのモデルを最初に読んでください。

講評で何度も出てくる指摘は、モデル間で名前がそろっていない、文字が小さい、手順を状態にしている、分かれ道に条件が無い、理由が書いていない、などです。提出前のチェックにそのまま使えます。

手順

この回は紙かテキストで構いません。ETラリーの「ヒントカードのQRを読んでゲートの位置を知る」について考えます。ETラリーの細かいルールは、docs/設計/ETラリー攻略設計.md と規約を見てください。

  1. 目標を数字で決めて、理由を書く
  2. 要求を4つ、番号つきで書く
  3. FMEA の表を作る
  4. 外にあるものと、やり取りする情報を書き出す

演習

演習15-1　要求を番号つきで書く

次の表を埋めてください。

番号 種類 要求 確かめ方（数字で）
REQ-1 機能 ヒントカード1・2のQRを読む
REQ-2 機能
REQ-3 非機能（信頼性）
REQ-4 非機能（性能効率性）

演習15-2　FMEA

次の3つについて、原因、どうなるか、深刻さ（1〜5）、起きやすさ（1〜5）、対策を書いてください。対策が、演習15-1のどの要求に入るかも書きます。

  • QRが読めない
  • 復号キーを打ち間違える
  • ゲートの位置を読み違える

演習15-3　困ることの因果

外から来る原因（照明、床の摩擦など）→ 困ること → 対策、を1組、線でつながる形で書いてください。「プログラムをモジュールに分ける」のような作り方の方針は対策ではありません。走行体がすることを書きます。

答えの例 `docs/後輩育成/練習/06_モデル図/答え/要求図とFMEA_答え例.md` にあります。

演習15-4　講評を読む

先輩と一緒に、2026年のアプライドクラスの講評を開いて、いちばん評価の高かったチームの良かった点から来年まねしたいことを3つ、うちのチームへの指摘から来年いちばん先に直すことを3つ書いてください。

次回までに

次回から実機です。走行体を触るので、先輩の都合を聞いて日程を決めてください。
